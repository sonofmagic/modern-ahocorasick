## 契约与验收条件

改动保持公共 API、原文字素边界、UTF-16 半开区间、重复词条顺序、独立匹配对象、ESM/CommonJS 入口与现有持久化格式。默认继续使用紧凑后端。

约定门槛为：普通、无命中和长 ASCII 的完整/选中扫描中位耗时至少降低 20%；大词典构建峰值 RSS 至少降低 40%；冷构建耗时最多增加 10%；扫描与保留内存不出现可复现的超过 5% 的退步。下文比值为 **新实现耗时 / 基线耗时**，越小越快。测量结论只适用于当前语料与环境，不代表普遍保证。

## 第一阶段：修复转换文本的增量流

`/text` 的匹配、分词、替换统一接入共享流式核心。稳定命中可以在 EOF 前从 `write()` 返回，默认 token 不再重叠。转换后的文本在拼接后继续增量分段，保留归一化后跨片段组合时的全文查询语义，包括兼容 Hangul。重叠选择之前会检查原文字素范围完整性、原文词边界和保护区。

流会清理已经提交的原文、转换尾、坐标映射与过期候选；结束、取消、溢出与回调异常都会释放保留状态。缓冲限制遵循 `maxBufferLength ?? maxBufferedUnits ?? 1_048_576`，覆盖转换层尚未提交的原文，保留显式 `Infinity`。过滤器读取原文，preview 使用独立扫描状态。

调用方必须同时消费 `write()` 和结束方法返回的结果，各入口原有终止契约保持不变。回归覆盖提前命中漏替换、默认 token 重叠、缓冲限制绕过、所有 UTF-16 切分位置、折叠扩展、兼容连字、Hangul、组合字符、ZWJ 序列、代理项切分、原文词边界、保护语法和 preview 状态。

### 持续消费结果后的保留内存

每个版本/策略运行三个独立进程，反复输入相同的 80 单位文本块，立即消费所有输出，并在 GC 后测量堆增量。词典与输入块在内存基准点之前已经存在。下表为中位数，单位 KiB；此实验中 ArrayBuffer 增量始终为零。

| 策略               | 实现     | 40,000 UTF-16 单位 | 120,000 单位 | 400,000 单位 | finish 和 cancel 后仍保留句柄 |
| ------------------ | -------- | -----------------: | -----------: | -----------: | ----------------------------: |
| `all`              | 基线     |            2,031.0 |      3,848.7 |     14,707.8 |                      14,666.8 |
| `all`              | 第一阶段 |              263.7 |        268.1 |        264.0 |                         158.5 |
| `leftmost-longest` | 基线     |            2,899.6 |      6,388.9 |     23,208.3 |                      23,179.2 |
| `leftmost-longest` | 第一阶段 |              271.1 |        275.7 |        271.1 |                         158.4 |

累计输入增长十倍时，新实现的测量值基本持平。在 400,000 单位、尚未 EOF 时，新 `leftmost-longest` 流已输出最终 80,000 条中的 79,997 条，基线此时尚无输出。最终数量与包含词条索引和范围的完整摘要一致。两个 `all` 流都能增量输出，但基线继续保留过期映射。

上述增量包含运行时/JIT 噪声，不能视为流状态的精确大小；不包含调用方保存的结果、当次输出数组、原生 ICU 存储和峰值 RSS。生命周期测试另外确定性验证了坐标映射有界并会释放。应用若主动保存全部结果，仍会占用与输出规模成比例的内存。

第一阶段还对普通、Unicode 和密集后缀输入运行五轮独立进程检查，测量默认扫描器的 `search`、`count`、`match`、leftmost-longest 迭代与替换。15 项比较均未超过 5% 退步门槛。这项检查针对默认扫描器，不是转换流的吞吐测试。

原始数据：[流式保留内存](./benchmarks-stream-optimization.json)、[默认扫描器检查](./benchmarks-stream-core.json)。二者均使用第一阶段提交 `b6ebdce`；实现摘要为 `593af04bb53db03a3dd84c0be75c30ec04dc51cbd6e863af74db75d6a0e1fb7a`。

## 第二阶段：ASCII 完整输出与选中扫描

第二阶段为完整输出和两种 leftmost 策略接入了已有的安全 ASCII 前缀扫描。ASCII 与原生字素分段各自保持读取位置，切换时保留自动机状态、选择候选与绝对偏移。CRLF、组合字符与 Unicode 继续使用原生回退；没有全文预扫描，也不增加逐字素包装对象。每条匹配结果仍然独立。

第二阶段与原始基线对比，每项运行五轮独立进程，每进程预热后采集七个批量样本。各表格单元为基线 → 第二阶段毫秒数，以及耗时比。

| 长 ASCII，提前命中 | 7.543 → 2.399 (0.318×) | 7.593 → 2.280 (0.300×) |   7.824 → 2.770 (0.354×) |     7.687 → 2.732 (0.355×) |

目标 ASCII 场景耗时降低 63%–72%，超过 20% 门槛。长输入各行均消费完整迭代器，这些操作中的提前命中不代表提前退出。普通文本的 leftmost-longest 替换由 2.149 ms 降至 0.806 ms（0.375×）；四类目标 ASCII 场景的替换耗时比为 0.292×–0.375×。

### 自适应完整枚举分派

实现保留单向 ASCII/原生扫描，并按词典选择完整枚举路径。编译后的任一状态聚合输出达到 32 条时，`search()` 和全部匹配迭代会使用较小的原生分段生成器。构建和反序列化各通过下标遍历计算一次这个私有标记，不改变公共 API 或持久化格式。计数和选中匹配扫描不使用该回退。

这一选择限制了每个状态可能产生大量输出时的生成器开销，也有明确代价：符合回退条件的词典，即便某次输入没有命中或只有少量命中，仍使用原生分段。因此 20% ASCII 改善目标对应上面的普通/无命中/长输入测试语料，不适用于任意词典的无命中输入。[七轮完整枚举专项对照](./benchmarks-dense-dispatch.json) 覆盖密集后缀、重复词条、普通文本、Unicode 与 ASCII 前缀；解读完整测试集时，还需纳入 `output-heavy-miss` 和 `output-heavy-sparse` 场景。

## 第三阶段：直接构建紧凑表

唯一的内部 builder 将字素统一编号，叶节点和单出边节点采用数字块存储，只有分叉节点分配 Map。每个输入词条记录一个终态，按输入顺序填充终态区间，直接生成紧凑转移数组。failure、output 和聚合计数使用最终的 TypedArray 队列；临时构建块的数据进入最终表后即可释放。小词典从较小的首块开始分配。构建期间还使用最多 256 个精确词条字符串的缓存，复用已经计算的终态和长度，同时保留每个重复词条及其输入顺序。匹配器不保留这个缓存。

双数组编译器和文档图都消费同一份紧凑构建结果，不再重建原来的逐节点对象图。已有序列化词典仍然可读，内部编号变化不要求新序列化字节完全相同。

构建与扫描的短转移循环有意保持独立。避免构建阶段偏重根节点的调用进入扫描器 JIT 反馈，是一项设计防护，不能当作已证实的早期耗时异常原因。下方的配对种子诊断确认随机字符串哈希布局会干扰测量。

以下中位数来自包含有界词条缓存的最终源码 `dd97451`，每个规模/版本使用配对哈希种子运行七个独立冷进程。构建耗时不包含生成输入与加载模块；峰值 RSS 包含进程运行时、输入、原生分配、临时构建数据与最终表。保留堆不含预先存在的词条字符串，ArrayBuffer 存储单独报告。

|    词条数 | 冷构建，基线 → 新实现 | 耗时降低 | 峰值 RSS MiB，基线 → 新实现 | 峰值降低 | 保留堆 MiB，基线 → 新实现 | 保留 ArrayBuffer MiB，二者相同 |
| --------: | --------------------: | -------: | --------------------------: | -------: | ------------------------: | -----------------------------: |
|    10,000 |      31.94 → 20.74 ms |    35.1% |              106.30 → 71.63 |    32.6% |               0.55 → 0.54 |                           1.60 |
|   100,000 |     186.38 → 92.05 ms |    50.6% |             407.11 → 140.38 |    65.5% |               3.50 → 3.49 |                          16.02 |
| 1,000,000 |  1,945.30 → 797.32 ms |    59.0% |           2,300.22 → 660.16 |    71.3% |             34.22 → 34.21 |                         160.22 |

十万和百万词条的峰值降低超过 40% 门槛，三个规模的构建都更快。各规模的 ArrayBuffer 字节数精确相同，保留 JS 堆略低。一万词条的整进程 RSS 降低 32.6%，固定运行时成本在较小进程中占比更高。历史模块通过 data URL 加载，加载器存储有所不同；原始数据保留了构建前 RSS，便于检查这一差异。

`count()` 探针使用预热后的七个校准批次。一万、十万、百万词条的最终耗时比分别为 0.9861×、0.9958×、0.8958×，均未超过 5% 退步门槛。这些规模探针是对更广泛扫描器对照的补充。

[最初三轮数据](./benchmarks-builder-initial.json)、[较早的七轮快照](./benchmarks-builder-before-scan-isolation.json) 和[词条缓存之前的快照](./benchmarks-builder-optimization.json) 保留供审计。最终方法在保留内存测量前等待三次 GC/任务轮转，避免将延迟释放的缓冲区归入词典。构建峰值 RSS 在这些 GC 之前记录。[初次完整扫描器对比](./benchmarks-optimization-initial.json) 和[七轮复测](./benchmarks-optimization-initial-recheck.json) 保留早期异常，二者均早于最终实现和配对种子测量方法。

原始数据：[最终七轮构建规模测量](./benchmarks-builder-final.json)，提交为 `dd97451`；实现摘要为 `c7af20de2e8a6a0064b3755ef656d653b0e6d469429ac614a7f0c03d5bc32a6c`。

### 小词典的重复构建

预热后的重复构建与每个冷进程只构建一次的规模实验是不同负载。`dd97451` 的[七轮构建器复测](./benchmarks-final-builder-recheck.json) 包含有界词条缓存和输出密度下标遍历。重复词条密集场景的构建耗时为基线的 0.4808×（35.664 → 17.147 µs），共享前缀为 0.6629×（1.269 → 0.841 ms），Unicode 为 0.9505×。普通词典重复构建为 1.0725×（75.951 → 81.460 µs），实测增加 7.3%。不能用这项小词典预热构建结果替代冷构建验收。实现摘要为 `c7af20de2e8a6a0064b3755ef656d653b0e6d469429ac614a7f0c03d5bc32a6c`。

## 综合扫描证据

[五轮完整对照](./benchmarks-optimization.json) 覆盖 `0d10f03` 快照的 18 个场景、13 种操作。完整输出、选中输出、替换和计数的所有比较均未超过 5% 退步门槛。四项异常涉及存在性查询、加载或重复构建，需要结合下方的独立复测。该完整矩阵早于密度下标遍历、有界词条缓存和修订后的预热方法。

| 场景                 | `search`，基线 → 快照 ms | `search` 耗时比 | `iterate:all` 耗时比 | Leftmost-first / longest 迭代耗时比 |

### 存在性查询与恢复复测

首次[七轮复测](./benchmarks-optimization-recheck.json) 仍记录到 Unicode 存在性查询与共享前缀加载异常。独立的[原生模块存在性诊断](./benchmarks-native-presence-warmed-diagnostic.json) 从真实文件加载历史模块图，每个进程测量前额外执行 65,536 次预热。Unicode 存在性查询为 3.619 → 3.592 µs（0.9925×），七对比值均低于 1.05×。这确认原测时辅助函数预热不足：较慢的冷/JIT 批次可能在代码稳定前达到 25 ms 校准目标，不能据此认定库逻辑退化。

累计预热至少 250 ms 并使用密度下标遍历后，[七轮预热复测](./benchmarks-final-warmed-recheck.json) 中 Unicode 存在性查询为 0.9066×，共享前缀恢复为 0.9889×。随后 `dd97451` 构建器复测中，同两项为 0.9082× 和 1.0208×。该复测的共享前缀存在性查询曾按独立中位数之比记录 1.1324×，配对比值中位数约 1.0213×，并有一个较大异常值。对同一实现进行[独立七轮仅存在性复测](./benchmarks-presence-final-recheck.json) 后，结果为 0.2951 → 0.3041 µs（1.0304×），没有异常项；进程间 MAD 为 0.0132 → 0.0049 µs。此前 13% 差异没有独立复现。这些微小耗时保留绝对值与两组数据供审阅。

### 词典保留内存

[七轮保留内存对照](./benchmarks-retained-optimization.json) 覆盖全部 18 个场景，不执行操作计时。它持有 `max(10, min(1000, floor(100000 / patternCount)))` 个匹配器，记录实际副本数，并将 GC 后增量除以副本数。小词典最多持有 1,000 份，降低一次性运行时/JIT 分配的影响；快照之前等待三次 GC/任务轮转。

这些场景的保留 JS 堆比值为 0.99292×–1.00823×，即 −0.71% 至 +0.82%；每个场景的 ArrayBuffer 字节数均精确相同。测量构建摘要为 `6716d18808b34e066dc30eaaaa8b90d773adc567feda47150f18e51b0283296c`，已包含密度下标遍历，尚未加入词条缓存。仅构建期间存在的缓存不属于匹配器保留状态；上方最终规模实验已单独测量其冷构建峰值，并确认缓冲字节不变、堆略低。词典保留内存、瞬时构建峰值和调用方保存的结果是不同指标。

## 测量方法与复现

直接对比应使用 pnpm 12.5.1 和相同的 Node/ICU 环境。基准串行运行，避免构建或测试争抢资源。耗时是独立进程中位数的中位数；JSON 保存各次样本和进程内/进程间中位绝对偏差。疑似超过 5% 的退步需要七轮独立进程复测，并结合绝对耗时与噪声判断。亚微秒提前退出的比值尤其容易受运行时开销影响。

扫描器、规模与版本对照使用预先确定的 V8 哈希种子：`104729 + roundIndex * 7919`。同一轮的各版本使用相同种子，不同轮改变种子，不会根据结果挑选种子。这样既控制了针对较小字符串字母表反复查询未命中时的噪声来源，也采样了多种哈希布局。计时现在要求累计预热至少 250 ms，且最后批次至少 25 ms，或已经达到每批 1,048,576 次上限；此前上限为 4,096。数据记录 `warmupMs` 和 `warmupIterations`，单次较慢的初始批次不再能提前结束校准。

[七种种子的计数诊断](./benchmarks-paired-count-diagnostic.json) 对 `ascii-early-unicode` 使用基线/当前实现配对种子，交替进程顺序。进程中位数之比为：`count` 0.99754×，`countByPattern` 0.99222×；每对 `count` 比值均在 0.98034×–1.02080×。此前约 9% 的计数差异在这一控制下没有保持，不支持将其归因于稳定的扫描代码退步。该诊断只针对这些操作和这份语料，不代表完整测试集的最终验收。

公共保留内存测量辅助函数也采用三次 GC/任务轮转，待临时缓冲区释放后再采集保留快照。较早数据仍保留其原始测量方法，不会被改标成使用新辅助函数的结果。

运行器按当前包结构构建历史源码的多入口模块图，对所有生成的 ESM 模块计算摘要，在测量前记录环境/提交信息。新数据还记录 `runnerSha256` 和明确的计时/内存方法；版本复测要求运行器、实现与环境相同。每个完成的子进程都会追加到 JSONL 日志，后续失败不会丢掉已有数据。`BENCH_RECORD_FILE` 可指定路径，默认临时路径输出到 stderr。数据也会注明工作区是否存在未提交改动，实际测量构建由实现摘要确定。
